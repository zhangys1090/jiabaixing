一、Windows 测试全绿（审计套件）

根因定位：通过最小复现证实，本机（Windows + Python 3.13）在 tempfile.TemporaryDirectory() 退出清理时，即便 SQLite 连接已 with 正常关闭，OS 仍会短暂持有 .db 文件锁，导致 PermissionError: [WinError 32]。因此单纯 close() 不足以消除锁，需「显式关闭持久连接 + 健壮 teardown」双管齐下。

修复动作

  • teardown 健壮化 审计套件全部 tempfile.TemporaryDirectory() 加 ignore_cleanup_errors=True，吸收 Windows 残留锁，保证清理不抛错。
  • 显式 close() 连接 4 个 KnowledgeGraph 用例在 graph.close() 后追加 store.close()——释放持久连接（KnowledgeStore._conn），这是真正持有文件句柄的一方。
  • 认知修正 用户提到的「2 个 KnowledgeGraph 过期测试（extract_entities→add_entry）」经核查逻辑本身正确，实际同样仅因 teardown 锁失败——已随上述修复一并转绿。

结果：test_five_subsystems_audit.py 由 46 通过 / 12 失败 → 58/58 全通过，达到 AGENTS.md「测试 100% 通过」门槛（所指审计套件）。

二、② 主动学习：同错重复率指标

在 agent/knowledge/failure_learner.py 新增错误签名聚合与量化指标，使「主动学习效率」可度量。

  • _signature(action, error)：取「动作 + 错误首行前 80 字符」提炼稳定签名，规避堆栈噪声把同一根因识别为多类错误。
  • learn_from_failure 每次调用自动累计 _error_counts / _total_failures / _unique_signatures。
  • recurrence_rate() = (总失败 − 唯一签名) / 总失败；越接近 1 表示反复踩同一坑。
  • get_metrics() 输出：total_failures / unique_signatures / repeated_failures / recurrence_rate / top_repeated_errors。
metrics = learner.get_metrics()
# {'total_failures':4, 'unique_signatures':2,
#  'repeated_failures':2, 'recurrence_rate':0.5,
#  'top_repeated_errors':[{'signature':'fs_delete::权限不足...','count':3}]}

新增用例 test_failure_learner_recurrence_metric：3 次同因失败 + 1 次异因，断言 recurrence_rate == 0.5 且高频签名 count==3。

三、③ Planner 生成阶段风险拆分 + 前端确认 UI

目标：规划器在生成阶段即把每一步拆为「需审批 / 可自动」，并驱动既有前端确认 UI。

后端

  • 新增共享模块 agent/tools/risk_level.py（classify_risk / requires_approval），供 Planner 与 RiskPrecheck 复用，避免 DRY 违规。
  • PlanStep 增加 requires_approval: bool；ExecutionPlan 增加 pending_approval_steps()。
  • Planner._annotate_risk(steps)：在 _plan_complex 主路径 / 增量重规划 / replan 三处生成后按工具风险等级标注，high/critical → requires_approval=True。
  • RiskPrecheck 复用共享分类器并同步标注 requires_approval；新增 plan_to_approval_requests(plan) 适配器，把待审批步骤转为既有 ApprovalDialog 的 ApprovalRequest 形状（id/toolName/params/riskLevel/timestamp/status）。
  • ApprovalManager.preview_plan_approvals(plan)（异步、非阻塞）：规划阶段即把「需审批」步骤推为预览请求并通知监听方；执行期 request_approval 命中同工具时复用该预览请求——实现「规划预览一次、执行即放行」。
  • LoopController 在 annotate_plan 后 await preview_plan(plan)（主规划 + replan 两处）。
    闭环 Planner 标注 → Controller 推送预览 → 前端 ApprovalDialog（GET /api/approval/requests 拉取、/api/approval/respond 回传）→ 执行期复用审批结论。

前端

既有的 src/frontend/src/components/ApprovalDialog/ 已按 riskLevel 渲染风险徽标与批准/拒绝按钮，并能消费上述请求形状——无需新建组件即完成「配合前端确认 UI」。

新增用例：test_planner_annotates_risk_and_splits_approval（low/high/critical 标注 + pending 过滤）、test_plan_to_approval_requests_shape（请求形状对齐）、test_approval_preview_reuse_at_execution（规划预览在执行期被复用、pending 清零）。

四、④ V4 Flash Function Calling 真实工具选择器

在 agent/mcp/orchestrator.py 新增 LlmToolSelector，实现「发现 → LLM 选择 → 执行」闭环中的真实 LLM 选择环节。

  • tool_definition_to_openai_schema(def)：把 ToolDefinition（含 ToolParameterDef）转为 OpenAI function-calling schema。
  • LlmToolSelector.select(query, definitions)：通过 LLMProvider.chat_with_tools(messages, tools, tool_choice="auto") 调用 V4 Flash 原生函数调用，解析结构化 tool_calls → ToolCall(name, params)（参数 JSON 容错）。
  • 与既有 RuleBasedSelector 实现同一 ToolSelector 协议，可无缝替换进 MCPToolOrchestrator.select_and_execute。
selector = LlmToolSelector(v4_flash_llm)
calls = await selector.select("抓取 https://example.com", reg.get_all_definitions())
# -> [ToolCall(tool_name="web_fetch", params={"url":"https://example.com"})]

新增用例 test_llm_tool_selector_parses_function_calls：mock LLM 返回 tool_calls，断言解析出的工具名与参数。
