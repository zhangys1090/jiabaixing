### Major（重要） - 6 个

#### M1: ImplicitFeedbackCollector 事件监听器缺少错误隔离

**问题描述**:
`onUserMessage` 方法中依次调用多个检测方法（isSatisfactionExpression、isFollowUp、isTopicSwitch、isRetry），但没有 try-catch 保护。如果其中任何一个检测方法抛出异常，会导致整个消息处理中断，后续的检测和状态更新都不会执行。

**影响范围**:

- ImplicitFeedbackCollector 模块
- 用户消息处理流程
- 可能导致反馈收集失效

**代码位置**:

```typescript
// src/evolution/ImplicitFeedbackCollector.ts:222-282
onUserMessage(data: Record<string, unknown>): void {
  if (!this.enabled) return;

  const now = Date.now();
  const content = data.content as string || '';

  // 检测满意度表达
  if (this.isSatisfactionExpression(content)) { ... }

  // 检测追问
  if (this.lastAiMessageTime > 0 && ...) {
    if (this.isFollowUp(content)) { ... }
  }

  // 检测话题切换
  if (this.isTopicSwitch(content)) { ... }

  // 检测重试
  if (this.isRetry(content)) { ... }

  this.lastUserMessageTime = now;
}
```

**修复建议**:

1. 每个检测逻辑用 try-catch 包裹，或整个方法用 try-catch 包裹
2. 确保即使某个检测失败，其他检测和状态更新仍能正常执行
3. 异常时记录 warn 日志，不影响主流程

**风险等级**: 中高 - 可能导致反馈收集功能部分失效，但不影响主业务

#### M2: LoopObserver 中 toolSuccessRate 统计逻辑错误

**问题描述**:
`toolSuccessRate` 每次工具调用结束时都重新计算，但只基于当前 trace 的工具调用，而不是历史所有工具调用。这导致统计数据名不副实，每次循环结束后成功率都会被重置。

**影响范围**:

- LoopObserver 模块
- 工具成功率统计数据不准确

**代码位置**:

```typescript
// src/harness/loop/LoopObserver.ts:367-375
// 更新统计
this.statistics.totalToolCalls++;
this.toolTotalDuration += toolCall.duration;
if (this.statistics.totalToolCalls > 0) {
  this.statistics.averageToolDuration =
    this.toolTotalDuration / this.statistics.totalToolCalls;

  const successfulTools = this.currentTrace.toolCalls.filter(
    (t) => t.success
  ).length;
  this.statistics.toolSuccessRate =
    successfulTools / this.currentTrace.toolCalls.length;
}
```

**修复建议**:

1. 增加全局的成功工具调用计数（successfulToolCalls）
2. toolSuccessRate = successfulToolCalls / totalToolCalls
3. 当前 trace 的成功率可以单独统计，但不应覆盖全局统计

**风险等级**: 中 - 统计数据不准确，可能误导调试和分析

#### M3: LearningStatusReporter 缺少输入参数校验

**问题描述**:
`generateReport` 和 `generateSummary` 方法直接使用 metrics 参数的各个字段，但没有校验 metrics 是否为 null/undefined，也没有校验必要字段是否存在。如果传入不完整的 metrics 对象，会导致运行时错误。

**影响范围**:

- LearningStatusReporter 模块
- 调用方如果传入异常数据，会导致报错

**代码位置**:

```typescript
// src/evolution/LearningStatusReporter.ts:29-109
static generateReport(metrics: UnifiedEvolutionMetrics): string {
  const lines: string[] = [];

  lines.push('');
  lines.push('  📊 学习状态报告');
  // ...
  lines.push(`    总交互次数: ${metrics.summary.totalInteractions}`);
  lines.push(`    总优化次数: ${metrics.summary.totalOptimizations}`);
  // ...
}
```

**修复建议**:

1. 方法开头添加参数校验，如果 metrics 为 null 或缺少必要字段，返回友好的错误提示或默认值
2. 使用可选链操作符（?.）增加健壮性
3. 提供默认值，确保即使数据不完整也能生成报告

**风险等级**: 中 - 可能导致报告生成失败，但不影响核心功能

**影响范围**:

- ImplicitFeedbackCollector 模块
- 统计数据的准确性和可信度

// src/evolution/ImplicitFeedbackCollector.ts:354-356
// 今日/本周统计（简化实现）
this.statistics.todayCount++;
this.statistics.weekCount++;
```

**修复建议**:

1. 方案A：修改字段名，改为 `sessionCount`（会话内计数），更符合实际行为
2. 方案B：实现真正的日期重置逻辑，每天/每周清零
3. 在注释中明确说明当前是简化实现，避免误导

**风险等级**: 中低 - 统计数据不准确，但不影响功能

#### M5: 单例模式滥用，不利于测试和扩展

**问题描述**:
4 个新增文件中有 3 个使用了单例模式（ImplicitFeedbackCollector、UnifiedContextBuilder、LoopObserver）。单例模式虽然方便，但有以下问题：

1. 难以进行单元测试（无法创建独立实例）
2. 状态全局共享，测试之间容易互相影响
3. 不利于扩展（如果需要多个实例怎么办？）
4. 隐式依赖，不便于理解模块间的关系

**影响范围**:

- 所有使用单例模式的模块
- 未来的测试工作和代码维护

**修复建议**:

1. 短期：保留单例，但添加 `resetInstance()` 或 `destroy()` 方法，便于测试重置
2. 中期：引入依赖注入，由上层管理实例生命周期
3. 长期：评估是否真的需要单例，很多场景下普通类 + 单例导出即可

**风险等级**: 中 - 主要影响可测试性和可维护性，不影响当前功能

/**
 * 生成 ASCII 迷你图（Sparkline）
 */
private static generateSparkline(values: number[]): string {
  if (values.length === 0) return '';

  const blocks = ['▁', '▂', '▃', '▄', '▅', '▆', '▇', '█'];
  const min = Math.min(...values);
  const max = Math.max(...values);
  const range = max - min || 1;

  let sparkline = '';
  for (const value of values) {
    const normalized = (value - min) / range;
    const index = Math.min(Math.floor(normalized * (blocks.length - 1)), blocks.length - 1);
    sparkline += blocks[index];
  }

  // 添加数值标签
  sparkline += `  ${(min * 100).toFixed(0)}% → ${(max * 100).toFixed(0)}%`;

  return sparkline;
}
```

**评价**: 这个方法实现得不错，逻辑清晰，边界条件处理得当（range 为 0 时的处理），数值标签增加了实用性。

### 7.3 最佳实践总结

#### 做得好的地方（值得保持）

1. **先设计再编码**
   - 每个文件头部都有详细的设计说明
   - 明确了功能、设计原则、使用场景
   - 这种做法值得推广

2. **默认安全/关闭**
   - 新功能默认关闭或轻量级
   - 有开关可以控制
   - 降低了风险和性能影响

3. **向后兼容**
   - 都是新增代码，不修改原有逻辑
   - 有降级机制，失败不崩溃
   - 集成风险低

4. **隐私意识**
   - 明确说明不存储敏感内容
   - 只记录摘要和统计
   - 数据最小化原则

5. **职责单一**
   - 每个模块只做一件事
   - 接口简洁，易于理解
   - 符合单一职责原则

---

#### 需要改进的地方

1. **错误处理是短板**
   - 很多地方缺少容错
   - 输入校验不足
   - 需要加强健壮性

2. **测试意识需要加强**
   - 单例模式不利于测试
   - 缺少单元测试
   - 测试应该和代码同步写

3. **细节决定质量**
   - JSDoc 不完整
   - 魔法数字多
   - 日志级别不统一
   - 这些细节积累起来会影响整体质量

4. **功能完成度要明确**
   - 框架和完成品要区分清楚
   - 避免给人"已经完成"的错觉
   - 明确标注状态和路线图

---

#### 给后续开发的建议

1. **代码质量左移**
   - 写代码前先想清楚错误处理和测试
   - 不要等出了问题再补
   - 质量是内建的，不是事后加的

2. **持续小步改进**
   - 不要追求一次完美
   - 每个迭代改进一点
   - 定期偿还技术债务

3. **重视可测试性**
   - 设计时就考虑如何测试
   - 避免单例和全局状态
   - 依赖注入是好东西

4. **文档和代码同等重要**
   - 好的代码也需要好的文档
   - JSDoc、README、示例都不能少
   - 文档是给未来的自己看的
