#### 迁移难点分析

**主要难点**：

1. **功能覆盖不完整**
   - ContextManager 功能大而全（~1500行）
   - UnifiedContextPipeline 只覆盖了 AI 上下文构建部分
   - 历史管理、压缩摘要、Token预算等功能需要单独迁移

2. **输出格式不兼容**
   - ContextManager.buildContext() 返回 ChatMessage[]
   - UnifiedContextPipeline.buildContext() 返回 UnifiedContext
   - 需要格式转换层

3. **调用点集中**
   - 主要使用方只有 AgentHarness 一个
   - 但 AgentHarness 是核心组件，改动风险高
   - 没有简单的、独立的调用点可以先迁移

4. **依赖关系复杂**
   - ContextManager 依赖 10+ 个子组件
   - 迁移需要同时处理多个依赖
   - 容易引入连锁反应

#### 建议方案

**渐进式迁移，分三个阶段**：

1. **第一阶段（已完成）**：创建适配器骨架
   - ✅ 创建 ContextManagerAdapter 类
   - ✅ 实现核心方法签名
   - ✅ 对已支持的功能进行委托
   - ✅ 对不支持的功能进行降级

2. **第二阶段（建议）**：完善适配器 + 试点迁移
   - 完善 buildContext 等核心方法的实现
   - 选择 1 个低风险调用点试点迁移
   - 验证功能等价性
   - 积累迁移经验

3. **第三阶段（远期）**：全面迁移 + 清理
   - 迁移所有调用点
   - 移除 ContextManager
   - 清理兼容层
