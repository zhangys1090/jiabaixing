2.1  Runtime 运行时 — python/agent/core/
─────────────────────────────────────────────────────────────────────

主引擎 engine.py：
  • AgentEngine 是整个系统的入口，组合了所有子系统
  • ReAct 系统提示词定义了 57 个工具的调用规范
  • 依赖注入：SubsystemRegistry + SubsystemSpec 管理子系统生命周期

对话循环 conversation_loop.py：
  • ConversationLoop — ReAct 模式多轮工具调用循环
  • 支持：多轮 LLM 调用 + 工具执行 + ThinkScrubber + 失败反思重试 + 流式输出
  • 迭代预算 IterationBudget：轮数/Token/连续失败上限

回合类型 turn_types.py：
  • TurnState: PENDING → PROCESSING → TOOL_CALLING → RESPONDING → COMPLETED/FAILED/RETRYING
  • IterationBudget: max_tool_rounds=10, max_total_tokens=50000, max_consecutive_failures=3

统一类型 types.py：
  • Permission 枚举：memory:read/write, file:read/write, code:execute, network:access, desktop:control, system:admin
  • RiskLevel 枚举：NONE → LOW → MEDIUM → HIGH → CRITICAL
  • PermissionCheckResult: allowed + missing + needs_confirmation

2.2  State 状态 — 桌面Agent + 上下文
─────────────────────────────────────────────────────────────────────

桌面Agent循环 DesktopAgentLoop.ts：
  • 观察 → 决策 → 执行 → 验证 → 汇报 五阶段
  • CODEX 风格：Sandbox/Snapshot/Manifest（checkpoint恢复 + 安全沙箱 + 工作空间描述）
  • 禁止动作清单：format, del /s, rm -rf, shutdown, reg delete 等

Q-Learning 决策引擎 DesktopDecisionEngine.ts：
  • DecisionState: screenComplexity, elementCount, activeWindows, consecutiveFailures, taskProgress
  • DecisionPolicy: epsilon-greedy (ε=0.3, α=0.1, γ=0.9)
  • Q表：状态桶编码 → 动作 → 价值，经验回放缓冲区

统一上下文管道 UnifiedContextPipeline.ts：
  • 三重组合：数据主权 × 记忆深度 × 主动关怀
  • 场景检测 → 情感分析 → 时间上下文 → 记忆检索 → 用户画像 → 主权评分

2.3  Decision 决策 — 任务调度 + 复杂度分析
─────────────────────────────────────────────────────────────────────

DAG 任务图 DAGTask.ts：
  • TaskNode: id, description, toolName, params, status, dependencies, priority, maxRetries=3, timeout=300s
  • TaskStatus: PENDING → RUNNING → SUCCESS/FAILED/SKIPPED/RETRYING
  • TaskPriority: LOW → MEDIUM → HIGH → CRITICAL
  • 拓扑排序 + 最大并行数(4) + 事件驱动

任务复杂度分析 TaskComplexityAnalyzer.ts：
  • 关键词驱动：high(分析/设计/开发/重构), medium(查询/计算/转换), conditional(如果/判断)
  • 并行度检测：parallel(同时/并行/批量) vs sequential(然后/接着/依次)
  • 领域标签：data / doc / pm
  • 多维度评估：时间复杂度 + 依赖复杂度 + 工具复杂度

动态任务调整器 DynamicTaskAdjuster.ts：
  • AdjustmentDecision: continue / retry / skip / replan / parallelize / sequentialize / abort
  • 监控阈值：progress<10%, time>10min, errors≥3, CPU>80%, Memory>85%

Tree-of-Thought TreeOfThought.ts：
  • 多路径推理：expand → evaluate(topK) → 递归展开
  • 默认：maxDepth=3, branchCount=3, evaluationTopK=2

场景感知调度器 ScenarioAwareScheduler.ts：
  • 时间调度 + 桌面环境感知 + Git变化感知 + 文件变更监听 + 主动推送

2.4  Task 任务 — 核心引擎
─────────────────────────────────────────────────────────────────────

JiabaixingCore JiabaixingCore.ts：
  • V5.0 架构：完全委托给 AgentHarness，保留记忆/调度/进化集成
  • 组件：PersonaCore + PersonaRules + LLMProvider + MemoryEngine + PerformanceMonitor + SecurityAuditor
  • 进化编排器：AGENT_BACKEND=python 时由 Python 接管，TS 侧为废弃存根
  • RL 训练轨迹导出：TrajectoryExporter + trajectoryBuffer

2.5  Evaluation 评估 — Python 端
─────────────────────────────────────────────────────────────────────

评估运行器 eval_runner.py：
  • EvalCase: id + input + expected_output + scoring_criteria
  • EvalRunner: 加载用例 → 运行引擎 → 评分 → 持久化 JSON

A/B 对比器 ab_comparator.py：
  • ABComparator.compare(): baseline vs candidate → regressions + improvements + verdict

评估门控 eval_gate.py：
  • EvalGate.check(): pass_rate≥0.8, average_score≥0.7, 趋势下降则拦截
  • EvalGate.check_ab(): 回归用例数检查 + A/B 裁决

2.6  Evolution 进化 — 双层体系
─────────────────────────────────────────────────────────────────────

V1 反馈学习层 engine.py：
  • 轻轻快速：从交互反馈优化参数和 Prompt，不修改代码
  • 持久化状态：tool_weights, prompt_examples, correction_rules, skills, compound_skills
  • 持久化关键词：我喜欢/偏好/记住/习惯/务必...

V2 自我进化层 v2_engine.py：
  • 重量深度：代码级自我修改，规划→验证→执行→回滚
  • V2EvolutionType: CODE_FIX / CODE_OPTIMIZATION / PROMPT_IMPROVEMENT / TOOL_ENHANCEMENT / ARCHITECTURE_CHANGE
  • EvolutionRiskLevel: SAFE → CAUTIOUS → RESTRICTED → FORBIDDEN（映射到统一 RiskLevel）

进化编排器 orchestrator.py：
  • 协调 V1 + V2，防止冲突
  • 冷却期 5min，自动检测间隔 5min
  • 验证回滚：pending_rollbacks 管理待回滚快照

架构关键约束：
  P2-3 收口（2026-08-03）：TS 侧进化引擎已正式收口为 AGENT_BACKEND=local 的废弃回退存根。
  生产路径（默认 AGENT_BACKEND=python）下，所有进化执行与数据由 Python agent.evolution
  经 PythonAgentBridge 接管。TS 端不再直接写文件。

3.1  Runtime 控制权：谁拥有最终行动权？
─────────────────────────────────────────────────────────────────────

Python AgentEngine.process_input() 是唯一的运行时入口：

  process_input(message)
    ├── security.check_command()          → 安全拦截（BLOCK 权）
    ├── context_file_registry + resolver  → 上下文注入
    ├── cross_session_memory              → 偏好注入
    ├── _assess_input_complexity()        → 复杂度分级
    ├── _resolve_execution_strategy()     → 策略路由
    │     ├── "multi_agent"  → _multi_agent_orchestrator.process_goal_with_loop()
    │     ├── "plan_exec_eval"/"react" → _process_with_loop()
    │     ├── "simple"       → _process_with_conversation()
    │     └── fallback       → _process_simple()
    ├── verification.check_output_safety() → 安全校验
    ├── verification.check_guardrails()   → 护栏校验
    ├── output_guardrail.check()          → 输出护栏
    ├── feedback_loops.run_all()          → 反馈闭环
    └── hook_manager.trigger(AFTER_LOOP)  → 后置钩子

关键发现 1：Python 端拥有完整的 Runtime 控制权链。
  从安全拦截 → 策略路由 → 执行 → 验证 → 护栏 → 反馈，全链路在 engine.py 内闭合。

关键发现 2：TS JiabaixingCore 在 AGENT_BACKEND=python（默认）下是薄网关。
  证据：
  • JiabaixingCore.ts:125: this.orchestrator = getActivePythonBridge() ? null : EvolutionOrchestrator.getInstance()
    — Python 模式下 TS 进化编排器为 null
  • JiabaixingCore.ts:140-145: isPythonBackend 分支直接 return，跳过所有本地 AI 组件初始化
  • AgentHarness.ts:113-120: Python 模式下仅初始化工具路由层，不初始化 Loop/Context/Verification/Constraints

⚠️ 风险点 A — TS 侧残留组件可能形成 Shadow Decision：
  • DesktopAgentLoop 仍然持有独立的 DesktopDecisionEngine（Q-Learning）和 DesktopActionExecutor
  • DesktopAgentLoop.ts:141: 决策路径 this._bridgeLlmAvailable() 检查 Bridge 是否可用，
    但如果 Bridge 不可用，会回退到本地 planActions()（规则匹配），此时 TS 侧独立决策
  • 结论：DesktopAgentLoop 在 Bridge 断连时存在隐性双主 — Python 不可用时 TS 自行决策执行
    桌面操作，绕过 Python 的安全/验证/护栏链

3.2  State 所有权：谁拥有 Canonical State？
─────────────────────────────────────────────────────────────────────

  状态            拥有者                                      持久化          Shadow 风险
  ──────────      ──────────────────────────────────          ────────        ──────────
  对话历史        ConversationHistoryManager(TS)               双写            ⚠️ 双写不一致
                  + SessionStore(Python)
  工具权重        EvolutionEngine._tool_weights(Python)        engine-state    TS 侧已收口 ✅
  Q表            DesktopDecisionEngine.qTable(TS)              内存            ⚠️ Python 无对应
  进化状态        EvolutionEngine._load_state()(Python)        engine-state    TS 侧已收口 ✅
  检查点          LoopCheckpoint(Python)                       各自独立        ⚠️ 两套体系
                  + StateSnapshotManager(TS)
  领域容器        AgentEngine.domains(Python)                  内存            ✅ Python 独占

关键发现 3：对话历史存在双写。
  engine.process_input() 中 session_store.add_message() 写 Python SessionStore，
  而 TS 侧 ConversationHistoryManager 也独立管理历史。两套存储之间没有同步机制。

关键发现 4：DesktopDecisionEngine 的 Q表是 TS 独占的 Shadow State。
  Python 端没有任何对应的桌面决策状态，Q-Learning 的经验完全在 TS 进程内积累，
  不经过 Bridge 同步到 Python。

3.3  Decision 唯一性：是否存在多源决策汇聚？
─────────────────────────────────────────────────────────────────────

Python 端决策链（权威）：
  _assess_input_complexity() → _resolve_execution_strategy() → strategy_impl.run()

TS 侧决策链（仅在 Desktop 模式激活）：
  DesktopAgentLoop.execute()
    ├── observe() → visionEngine.observe()
    ├── decide()  → llmPlanActions() [经Bridge] 或 planActions() [本地规则]
    ├── execute() → executor.executeTask()
    ├── verify()  → visionEngine.observe() (视觉验证)
    └── report()  → generateReport()

关键发现 5：桌面决策存在两条路径且无仲裁。
  • 路径 A（正常）：llmPlanActions() → 经 Bridge 路由到 Python LLM → Python 的安全/护栏生效
  • 路径 B（降级）：planActions() → TS 本地规则匹配 → 完全绕过 Python 安全链
  • 没有机制在路径 B 执行前检查 Python 是否可用并拒绝执行高风险操作
  • filterUnsafeActions() 仅基于硬编码黑名单（format, del /s, rm -rf 等），
    不经过 Python 的 CommandGuard / PermissionGuard / SchemaValidator

3.4  Evaluation 裁决权：能否真正阻止错误变更？
─────────────────────────────────────────────────────────────────────

EvalGate.check() 的裁决逻辑：
  if report.summary.pass_rate < 0.8:     → BLOCK
  if report.summary.average_score < 0.7: → BLOCK
  if trend == "declining":               → BLOCK

EvalGate.check_ab() 的裁决逻辑：
  if block_on_regression and len(regressions) > max_regressions: → BLOCK
  if ab_report.verdict == "regression":                        → BLOCK
  if candidate.pass_rate < min_pass_rate:                      → BLOCK

关键发现 6：EvalGate 有裁决能力但未被接入 Evolution 执行路径。
  追踪 EvolutionOrchestrator._trigger_optimization_cycle()：
  1. V1: should_evolve() → execute_evolution(plan) — 直接执行，无 EvalGate 检查
  2. V2: trigger_evolution(cause) — 内部完成 plan + execute + validate，
     但 validate 是自验证（EvolutionEngineV2 自己校验自己），不是独立 EvalGate

关键发现 7：V2 自修改存在"自己评估自己"的闭环。
  EvolutionEngineV2.trigger_evolution() 内部的验证步骤是自身的方法，
  不是委托给 IndependentEvaluationService 或 EvalGate。
  这违反了架构不可信原则：
    Evolution → 修改代码 → 自己评估 → 自己发布

关键发现 8：IndependentEvaluationService 有独立评估能力但未被 Evolution 消费。
  IndependentEvaluationService.evaluate() 能做任务完成度、数据接地性、安全性、质量四维评估，
  但在 Evolution 编排器中从未被调用。

3.5  Evolution 闭环：学习结果如何进入 Production？
─────────────────────────────────────────────────────────────────────

V1 反馈学习路径（轻量）：
  FeedbackSignal → _process_feedback_signal()
    ├── _update_tool_weight()     → tool_weights (影响工具选择)
    ├── _add_prompt_example()     → prompt_examples (影响 few-shot)
    ├── _learn_from_failure()     → correction_rules (影响重试策略)
    └── _schedule_persist()       → engine-state.json

  V1 消费点：tool_weights 被 StrategyAdapter 和 ConversationLoop 的工具选择逻辑消费。✅ V1 形成真实闭环。

V2 自修改路径（重量）：
  V2EvolutionCause → trigger_evolution()
    ├── generate_evolution_plan()  → LLM 生成修改方案
    ├── _execute_plan()           → 直接写文件（MODIFY_FILE/CREATE_FILE/DELETE_FILE）
    ├── _validate_evolution()     → 自验证（非独立）
    └── rollback if needed        → EvolutionRollback.rollback()

关键发现 9：V2 的学习结果直接写入文件系统，无 EvalGate 门控。
  _execute_plan() 中 MODIFY_FILE 动作直接 Path(file_path).write_text(content)，
  没有任何评估门控检查。

关键发现 10：V2 回滚机制存在但依赖检查点完整性。
  EvolutionRollback.create_checkpoint() 在修改前保存原文件内容，rollback()时恢复。
  但如果 V2 修改了多个文件且部分写入成功部分失败，回滚只能恢复已保存快照的文件，
  未保存的文件修改无法回滚。

3.6  验证回滚闭环（Orchestrator 层）
─────────────────────────────────────────────────────────────────────

Orchestrator 的验证回滚机制：
  _trigger_optimization_cycle():
    pre_snapshot = _take_baseline_snapshot()        # 拍基线
    # ... 执行优化 ...
    _pending_rollbacks[cycle_id] = pre_snapshot     # 加入待验证队列

  _check_pending_rollbacks(current_quality):
    if interaction_count - snapshot.interaction_count >= VERIFICATION_INTERACTIONS:
      if current_quality < baseline - ROLLBACK_THRESHOLD:
        _rollback_evolution()                       # 恢复 tool_weights

关键发现 11：Orchestrator 层验证回滚仅覆盖 V1 的 tool_weights。
  _rollback_evolution() 只恢复 self._evolution_engine._tool_weights，
  不回滚 V2 的代码修改。V2 的代码修改回滚依赖 EvolutionRollback，
  但 Orchestrator 没有在优化周期中调用 V2 的回滚。
