## 二、详细优化措施

### 2.1 缓存策略优化

#### 2.1.1 三级缓存架构

**问题**：单一缓存层，热点数据和冷数据混在一起，每次访问都要经过OrderedDict的查找。

**优化方案**：实现三级缓存架构

```
L0 微型缓存（最近1条）
    ↓ 超快命中（变量直接访问）
L1 结果缓存（LRU + TTL）
    ↓ 标准命中
L2 组件级缓存（每个组件独立）
```

**L0微型缓存特点**：

- 只存储最近1条请求的结果
- 纯变量存储，无字典查找开销
- 命中速度比L1快 2-3 倍
- 适用于重复请求场景

**预期收益**：

- 重复请求场景：缓存命中速度提升 30-50%
- 单请求场景：几乎无额外开销

#### 2.1.2 缓存键生成优化

**问题**：每次生成缓存键都要计算MD5哈希，开销较大。

**优化方案**：快速路径 + 分级哈希

```python
# 快速路径：短字符串直接拼接，避免MD5
if len(parts) <= 3 and all(isinstance(p, str) and len(p) < 100 for p in parts):
    return "|".join(parts)  # 比MD5快 5-10倍

# 长字符串：使用MD5保证长度可控
return hashlib.md5(key_string.encode("utf-8")).hexdigest()
```

**组件级缓存键特殊优化**：

- 组件名 + 短输入（<80字符）：直接拼接
- 组件名 + 长输入：只对输入部分做MD5

**预期收益**：

- 短输入场景：缓存键生成速度提升 5-10 倍
- 整体构建：缓存相关开销减少 20-30%

#### 2.1.3 批量过期清理

**问题**：每次 get 都检查 TTL，频繁调用 time.time()。

**优化方案**：批量清理 + 节流

```python
# 每100次get做一次批量过期清理
self._get_count += 1
if self._get_count >= 100:
    self._get_count = 0
    self._cleanup_expired()

# 节流：至少间隔5秒才清理一次
if now - self._last_cleanup_time < 5.0:
    return
```

**预期收益**：

- 减少 time.time() 调用：80%+
- 减少过期检查开销：90%+
- 命中路径更轻量

### 2.2 组件执行优化

#### 2.2.1 执行顺序缓存

**问题**：每次构建都要重新拓扑排序，O(n²)复杂度。

**优化方案**：执行顺序缓存

```python
# 生成缓存键：组件名称的有序组合
cache_key = ",".join(c.name for c in components)

# 检查缓存
cached = self._execution_order_cache.get(cache_key)
if cached is not None:
    return cached

# 未命中，计算执行顺序
ordered = self._dependency_resolver.resolve_execution_order(components)

# 缓存结果（限制缓存大小）
if len(self._execution_order_cache) < 100:
    self._execution_order_cache[cache_key] = ordered
```

**特点**：

- 以组件名称组合为缓存键
- 最多缓存100种组合（防止内存泄漏）
- 组件注册/注销时自动失效

**预期收益**：

- 常用组件组合：依赖解析开销减少 90%+
- 组件数量多时：效果更明显

#### 2.2.2 快速路径优化

**问题**：所有组件都要走完整的执行流程，包括创建结果对象、状态变更等。

**优化方案**：多层快速路径

**第一层：编排器快速路径**

- 1-2个组件：跳过依赖解析，直接执行
- 3个以下组件：跳过详细依赖检查

**第二层：组件快速路径**

```python
# 快速路径1：组件未启用 - 直接返回
if not self._enabled:
    return ComponentResult(
        component_name=self.name,
        status=ComponentStatus.DISABLED,
        execution_time_ms=0.0,
    )

# 快速路径2：不需要处理 - 直接返回
if not self.can_handle(request):
    return ComponentResult(
        component_name=self.name,
        status=ComponentStatus.SKIPPED,
        execution_time_ms=0.0,
    )
```

**预期收益**：

- 跳过的组件：开销减少 80%+
- 简单场景：整体构建速度提升 15-25%

### 2.3 数据结构优化

#### 2.3.1 轻量化结果对象

**问题**：每次执行都创建完整的 ComponentResult 对象，即使是跳过的组件。

**优化方案**：

- 跳过/禁用的组件：创建最小化结果对象
- 只在需要时计算统计数据
- 延迟填充非关键字段

#### 2.3.2 预分配与复用

**优化措施**：

- 列表预分配容量（已知大小时）
- 使用 extend 代替多次 append
- 避免不必要的深拷贝

**预期收益**：

- 内存使用：减少 10-20%
- GC压力：降低 15-25%

---

### 2.4 内存优化

#### 2.4.1 缓存大小限制

**优化措施**：

- 执行顺序缓存：最多100条
- L0微型缓存：固定1条
- L1结果缓存：可配置，默认100条
- L2组件缓存：每个组件最多 总缓存/5 条

#### 2.4.2 对象创建优化

**优化措施**：

- 减少临时字典/列表创建
- 字符串拼接优化（使用 f-string 或 join）
- 避免不必要的对象包装

## 五、最佳实践建议

### 5.1 性能最佳实践

#### 5.1.1 缓存使用建议

1. **启用缓存**：大多数场景下都应该启用缓存

   ```python
   orchestrator = UnifiedContextOrchestrator(use_cache=True)
   ```

2. **合理设置缓存大小**：
   - 小流量场景：50-100条足够
   - 大流量场景：200-500条
   - 内存受限：10-50条

3. **合理设置TTL**：
   - 实时性要求高：60-300秒
   - 实时性要求低：600-3600秒
   - 不关心过期：设置为0（永不过期，仅LRU淘汰）

#### 5.1.2 组件使用建议

1. **只注册需要的组件**：避免注册不必要的组件
2. **合理排序优先级**：常用的、快的组件优先级高一些
3. **使用 can_handle()**：在组件中实现快速判断
4. **禁用不需要的组件**：暂时不用的组件可以禁用

#### 5.1.3 请求优化建议

1. **保持请求一致性**：相同参数的请求更容易命中缓存
2. **控制历史消息数量**：历史消息越多，构建越慢
3. **使用 session_id**：相同 session_id 的请求更容易复用缓存

### 5.2 监控建议

#### 5.2.1 关键监控指标

1. **构建耗时**：
   - 平均耗时
   - P95/P99 耗时
   - 耗时趋势

2. **缓存指标**：
   - 缓存命中率
   - 缓存大小
   - 淘汰次数

3. **组件指标**：
   - 各组件执行时间
   - 各组件成功率
   - 组件降级次数

#### 5.2.2 告警阈值建议

| 指标         | 警告阈值 | 严重阈值 |
| ------------ | -------- | -------- |
| 平均构建耗时 | > 50ms   | > 100ms  |
| P99构建耗时  | > 200ms  | > 500ms  |
| 缓存命中率   | < 30%    | < 10%    |
| 组件失败率   | > 5%     | > 20%    |
