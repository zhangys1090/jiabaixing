# jiabaixing 综合开发能力评估方案

## 一、评估体系概述

### 1.1 评估目标
本方案旨在全面评估 jiabaixing 的前后端开发能力、架构设计能力、问题解决能力以及工程化实践水平。通过 24 个递进式任务，覆盖从基础功能实现到复杂业务逻辑处理的完整技术栈。

### 1.2 技术栈说明
| 层级 | 技术 | 版本 |
|------|------|------|
| 前端 | React + TypeScript | 18.2.0 / 4.9.5 |
| 前端样式 | styled-components / CSS | 6.4.1 |
| 前端组件库 | Ant Design | 5.15.0 |
| 后端 | Node.js + Express + TypeScript | ES2022 |
| 数据库 | SQLite + Chroma (向量) | better-sqlite3 |
| 通信 | WebSocket + REST API | ws ^8.20.0 |
| 测试 | Jest + ts-jest | ^30.3.0 |
| 代码规范 | ESLint v9 + Prettier | flat config |

### 1.3 评估维度
| 维度 | 权重 | 说明 |
|------|------|------|
| 功能完整性 | 25% | 需求实现程度、边界条件覆盖 |
| 代码质量 | 25% | 类型安全、代码规范、架构设计 |
| 性能表现 | 15% | 响应时间、内存占用、渲染效率 |
| 健壮性 | 15% | 错误处理、异常恢复、并发安全 |

#### T1: 前端主题切换组件

**需求描述**：
为 jiabaixing 前端实现一个可复用的主题切换组件，支持 Dark/Light 模式切换，并持久化用户选择。

**技术栈要求**：
- React 18 + TypeScript
- CSS Variables / styled-components
- localStorage API

**实现步骤**：
1. 在 `src/frontend/src/components/ThemeToggle/` 创建组件目录
2. 定义主题类型：`type Theme = 'dark' | 'light' | 'system'`
3. 实现 `ThemeToggle.tsx` 组件，包含：
   - 主题切换按钮（太阳/月亮图标）
   - 下拉菜单支持 system 选项
   - 切换动画效果（CSS transition）
4. 创建 `useTheme` Hook，管理主题状态：
   - 读取 localStorage 初始值
   - 监听系统主题变化（matchMedia）
   - 切换时更新 document.documentElement 的 data-theme 属性
5. 在 `App.tsx` 中集成 ThemeToggle

**验收标准**：
- [ ] 点击按钮可切换 Dark/Light 主题
- [ ] 刷新页面后主题选择保持不变
- [ ] 选择 system 时自动跟随操作系统主题
- [ ] 切换时有平滑过渡动画（300ms）
- [ ] 所有现有组件在两种主题下显示正常
- [ ] 代码通过 ESLint 检查，无 any 类型

**评分权重**：功能40% + 代码质量30% + 用户体验30%

#### T5: WebSocket心跳检测

**需求描述**：
为前后端 WebSocket 连接实现心跳检测机制，自动重连和连接状态管理。

**技术栈要求**：
- WebSocket API (browser)
- ws library (Node.js)
- 心跳定时器管理

**实现步骤**：
1. **前端**（`src/frontend/src/hooks/useWebSocket.ts`）：
   - 添加心跳发送逻辑（每 30 秒发送 `{ type: 'ping' }`）
   - 添加心跳超时检测（45 秒未收到 pong 认为断开）
   - 实现指数退避重连策略（1s, 2s, 4s, 8s, max 30s）
   - 暴露连接状态：connecting / connected / disconnected / reconnecting
2. **后端**（`src/ide/IDEConnectionManager.ts` 或新建）：
   - 监听 ping 消息，回复 pong
   - 检测客户端心跳（60 秒未收到 ping 断开连接）
   - 清理无效连接
3. 添加连接状态可视化（UI 显示 reconnecting 状态）

**验收标准**：
- [ ] 正常连接时每 30 秒发送心跳
- [ ] 服务端 60 秒未收到心跳自动断开
- [ ] 客户端 45 秒未收到 pong 触发重连
- [ ] 重连间隔按指数退避增长，最大 30 秒
- [ ] 重连成功后恢复之前的订阅状态
- [ ] 网络断开后自动恢复，用户无感知
- [ ] 有单元测试模拟网络断开/恢复场景

**评分权重**：功能40% + 健壮性40% + 性能20%

#### T7: 消息历史分页查询

**需求描述**：
为聊天系统实现基于游标的消息分页查询API，支持时间范围筛选和关键词搜索。

**技术栈要求**：
- SQLite 索引优化
- Cursor-based Pagination
- 全文搜索（SQLite FTS 或内存过滤）

**实现步骤**：
1. 创建 `messages` 表（如果不存在）：
   ```sql
   CREATE TABLE messages (
     id INTEGER PRIMARY KEY AUTOINCREMENT,
     session_id TEXT NOT NULL,
     role TEXT NOT NULL, -- 'user' | 'assistant' | 'system'
     content TEXT NOT NULL,
     timestamp INTEGER NOT NULL,
     metadata TEXT -- JSON
   );
   CREATE INDEX idx_messages_session_time ON messages(session_id, timestamp);
   CREATE INDEX idx_messages_timestamp ON messages(timestamp);
   ```
2. 实现分页查询 API：
   - `GET /api/messages?sessionId=xxx&cursor=xxx&limit=20&before=timestamp`
   - `GET /api/messages/search?sessionId=xxx&q=keyword&limit=20`
3. 使用游标（cursor）而非 offset，避免数据漂移
4. 实现消息导出接口 `GET /api/messages/export?sessionId=xxx&format=json|csv`
5. 添加查询性能监控（慢查询日志）

**验收标准**：
- [ ] 支持游标分页，返回 nextCursor
- [ ] 单页默认 20 条，最大支持 100 条
- [ ] 支持时间范围筛选（before/after）
- [ ] 关键词搜索响应 < 200ms（10000 条数据）
- [ ] 导出接口支持 JSON 和 CSV 格式
- [ ] 有数据库索引优化，查询计划无全表扫描
- [ ] 并发查询安全，无 SQL 注入风险

**关联验证**：
- T6 完成后，验证虚拟滚动 + 分页加载的协同工作

**评分权重**：功能35% + 性能35% + 健壮性30%

## 六、评估注意事项

### 6.1 公平性原则
1. 所有候选人使用相同的代码基线和评估标准
2. 评估过程中允许查阅官方文档，不允许搜索现成方案
3. 每个任务独立评分，不因前一个任务表现影响后一个

### 6.2 时间控制
1. 候选人可提前提交，但不可超时（培养时间意识）
2. 超时未完成的任务按当前实现状态评分
3. 连续 3 个任务超时，评估终止

### 6.3 沟通规则
1. 任务说明阶段可充分提问
2. 编码阶段仅允许澄清需求，不允许技术求助
3. 评审阶段进行技术讨论，但不改变评分

### 6.4 特殊情况处理
1. **环境问题**：如非候选人原因导致环境故障，暂停计时，修复后继续
2. **需求变更**：评估过程中发现需求歧义，统一由评估人解释，不扣分
3. **创新方案**：如候选人提出优于标准方案的实现，可加分
