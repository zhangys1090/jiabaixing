一、信号阻塞与拦截（Signal）

风险最高的一类：信号处理器一旦写错，进程会在崩溃/关闭时行为异常，且问题极难在测试中暴露。

#等级位置问题修复建议
2.1高 src/main.ts:439
src/main.ts:444		 uncaughtException / unhandledRejection 处理器仅 Logger.error 而不退出进程。Node 中一旦挂上 uncaughtException handler，默认的崩溃退出被覆盖，进程在可能已损坏的状态（内存/句柄/内部状态不一致）下继续运行；WS_ERR_INVALID_CLOSE_CODE 还被显式忽略。这是 Node 经典反模式，会导致"僵尸进程"。 记录后用 process.exit(1) 退出（或把危险工作放进子进程/worker 隔离）；unhandledRejection 建议计数到阈值再退出，避免无限累加。
2.2高 src/integration/gatewayWorker.ts:145
:154		 Worker 线程的 uncaughtException/unhandledRejection 同样只记录 + 发 IPC 不退出。Worker 在损坏态继续存活，父进程无法感知，可能造成任务静默丢失。 发送错误后调用 process.exit(1)；或 worker.terminate() 由父进程兜底重启。
2.3高 python/agent/gateway/forensics.py:227-228 SIGTERM/SIGINT 处理器内调用 self.record()（构造 dict、time.time()、构建 ShutdownRecord、可能写盘）——非 async-signal-safe：在持有 GIL 或非重入区收到信号可死锁/状态损坏。signal.signal 仅在主线程有效，子线程调用抛 ValueError 被静默 log.warning。更严重：handler 只记录、不发起关闭，SIGTERM 被拦截后进程不终止（除非主循环轮询某标志）。 handler 只置标志位 self._shutdown_requested=True（或 signal.set_wakeup_fd / 用 asyncio.loop.add_signal_handler）；记录动作移回主线程执行；主循环周期性检查并优雅退出。

二、错误被吞（Swallowed Errors）

2.1 API 层系统性静默 —— 高

现象：python/agent/api/ 下有 104 处 except Exception，捕获后返回 {"success": False, "error": str(e)} 给客户端，但服务端不记录任何日志、堆栈或指标。运维侧对失败完全不可见，只能靠用户反馈发现。

代表位置：

api/memory.py      :125,139,153,182,209,237,253,273,296,315,363,375,387,398,410,427,445,457
api/llm.py         :384,409,428,517,537,555,573,594,616  (+ SSE 生成器 :484)
api/canary.py      :51,63,75,87
api/compat.py      :113,155,650,843,898
api/feedback.py    :45,110
api/cognition.py   :42
api/health.py      :99,117,199,213,227,244,259,320,363,391

根因：ruff 门禁 E722(裸 except:)、S112(except:pass) 拦不住 except Exception: return {...} 形式，形成审计盲区。P0-3 引入的 log_ignored 也未在此类端点使用。

修复：① 每个 except Exception 在返回前补 log_ignored(log, "<模块>.<函数>", e) 或 logger.error(..., exc_info=True)；② 注册统一 FastAPI 异常处理器，集中记录 500 级错误；③ 新增 CI 规则（自定义 AST 检查，或 flake8-try-except-raise）抓"except 块既无 raise 也无 log"的模式。

2.2 错误类型误标 —— 中

api/cognition.py:42 · api/feedback.py:45 · api/feedback.py:110

try:
    body = json.loads(await request.body())
except Exception:
    return {"success": False, "error": "invalid JSON body"}

try 块本意只捕获 JSON 解析错误，却用裸 except Exception，使任何下游异常（DB 错误、KeyError、网络超时）都被误报为 "invalid JSON body"，真实原因被掩盖，排障被误导。

修复：改为 except json.JSONDecodeError 才返回该消息；其余异常按 2.1 记录并透传真实错误。

三、逻辑错误（条件 / 循环 / 边界 / 状态）

Python 静态启发式（可变默认参数、== None、== True/False）扫描结果为 0 处，说明基础反模式已清理。下列为在核心调度/循环模块中人工核实出的真实逻辑缺陷。

#等级位置问题修复建议
3.1高 python/agent/scheduler/cron.py:335-342 + 405/439 慢任务被每个 tick 重复派发。_tick 按 job.next_run <= now 派发，但 next_run 与 status="running" 都在 _run_job 异步执行完成后才更新（439/405 行）。派发经 MQ 后立即返回，调度锁 cron:sched:{id} 在 dispatch() 后即释放。于是：下一 tick 时 next_run 未推进且 status 仍非 "running"（_run_job 尚未开始），任务被再次派发。原用于防重的 status=="running" 守卫因异步时序完全失效。 派发时（_safe_dispatch 内）同步置 job.status="running" 并 self._save()；或将 next_run 推进提前到派发时刻；或将调度锁持有范围扩展到执行完成。
3.2中 python/agent/scheduler/cron.py:438 cron 表达式周期被退化为 +3600s。interval = _parse_interval(job.schedule) or 3600：对 cron 表达式（如 */5 * * * *）_parse_interval 返回 None，next_run 被设为 end + 3600，完全忽略真实 cron 周期。项目已实现 _next_cron_run()（159 行）却从未在此使用 → cron 语法任务会变成每小时跑一次。 若 _parse_interval 为 None 且 job.schedule 为 cron 表达式，改用 _next_cron_run(job.schedule) 计算下次运行时间。
3.3中 python/agent/scheduler/cron.py:307-318 stop() 无事件循环时泄漏锁与 MQ。stop() 在 except RuntimeError（无 running loop，如同步 teardown / atexit）分支直接 self._leader=None; self._mq=None; return，未调用 leader.stop() / mq.stop()。底层 Redis 领导者锁、调度锁与 MQ 连接未释放（只能等 TTL 过期），MQ 未停止。状态清理遗漏。 无循环时也同步释放底层资源（create_lock 的 Redis 连接、MQ 连接），或补 atexit/__del__ 兜底；至少记 warning 提示未释放。
3.4低 python/agent/loop/executor.py:915,938-945,1057 _retry_with_reflection 中 step.retry_count 在函数入口(+1) 与循环体内(1057 行, 每次 attempt +1) 双重自增，配合 max_reflection_retries = min(dynamic, step.max_retries) 与循环内 step.retry_count >= step.max_retries 守卫，计数逻辑可读性与边界易误判（当前实测不越界，但耦合脆弱，重构易引入 off-by-one）。 统一重试计数入口，避免两处自增；将"已尝试次数"与"最大次数"用独立变量表达并以断言保护边界。

已核实无问题的关键点（避免过度告警）

  • loop/executor.py 的反思重试循环：错误类型路由、替代工具迁移、经验回写逻辑完整，log_ignored 已用于内部异常 —— 功能正确。
  • api/health.py 的 subsystems_health / ignored_exceptions_health 设计上"永不报 unhealthy"，属有意取舍。
  • Python 端无裸 except:，P0-3 静默异常治理有效。
