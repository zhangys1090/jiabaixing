方法：实时探测（grep / read / 真实代码路径），不采信文档宣称。所有结论附 file:line 证据。

一句话结论：14 个工具均已注册启用，基础功能可用，但存在 3 个 P0 级系统性风险（文件沙箱逃逸、审批(HITL)在执行层未强制、超时无法真正中止）+ 多处 P1 安全/正确性缺陷。认知类工具（能思）在 TS 侧被降级为规则启发式，与 Python 主实现能力不对称。整体尚未达到“一致、可靠、高效”的生产态。

二、系统性风险（跨能力，P0）

P0-1 · 文件沙箱逃逸（能控）

file_read 对绝对路径直接采用、无项目根约束：src/harness/tools/file/file_read.ts:99-101 —— path.isAbsolute(rawPath) ? rawPath : path.resolve(...)。传入 /etc/shadow、C:\Windows\... 等可读任意文件。当注入 deps.readFileContent 时，MAX_FILE_SIZE 2MB 上限被绕过（:96-97 直接整文件读取，:126-133 的大小检查仅作用于本地分支）。

file_list 同理：src/harness/tools/file/file_list.ts:78-80 绝对路径直接 readdir，无 containment；且递归跟随符号链接（:105 entry.isDirectory()）无环路保护，max_depth 参数被硬编码为 10（:90），描述承诺的 max_depth 形同虚设。

P0-2 · 审批(HITL)在执行层未强制（能控 / 能写）

ToolRegistry.execute() 仅做 Schema + Permission 前置，从不调用 ApprovalEngine：src/harness/tools/registry/ToolRegistry.ts:254-305。PermissionGuard 对高风险工具返回 needsConfirmation:true（:288 只判断 allowed），但 execute 层忽略该标志。后果：授予 SYSTEM_ADMIN 后 shell_exec 无需任何人工确认即执行；code_fix 等声明 requiresConfirmation:true（code_fix.ts:34）亦不生效。且 setPreChecksEnabled(false)（:571-577）可一键关闭全部门禁。

P0-3 · 超时无法真正中止非协作式工具（能控 / 能抓）

execute 用 Promise.race([tool.execute, createTimeoutPromise(timeout)])（ToolRegistry.ts:313-322），超时仅 reject 而不取消底层操作。若工具使用无 AbortSignal 的全局 fetch 或 execSync，底层进程/请求继续运行 → 资源泄漏。更糟：execSync 为同步阻塞事件循环，期间 setTimeout 根本不触发，超时对同步工具完全失效。

P1 · 无瞬态失败重试 / 自愈未接入 TS 路径

TS 执行链 零重试（一次失败即返回）。Python 侧 tool_self_healing.py 的 heal() 仅做参数修正→替代工具→降级，不处理 429/5xx/限流退避，且其 RETRY 枚举未被使用；该自愈链未挂到 TS 执行路径（仅 Python 引擎侧）。

P1 · 无真实并发上限 / 无成本预算（TS 侧）

PermissionGuard 仅有会话级计数（maxToolCalls:100），无 per-agent 信号量；ToolCallGuard 的限速/去重 MAX_SAME_TOOL=2（ToolCallGuard.ts:62-65）未被 TS 执行链引用，形同死代码。TS 侧对 image_generate / tts_speak / LLM 类工具无任何 token 或费用预算（成本守卫仅 Python 侧存在）。

四、增强优化方案

设计原则：① 先补安全与一致性（P0），再补弹性与效率（P1），最后补协同与体验（P2）；② 贯彻 AGENTS.md §0.1 —— Agent 核心能力以 Python 为主实现，TS 收敛为薄壳/桥；③ 所有改动须有单测守护，尤其是错误与边界路径。

A. 安全加固（P0，最高优先）

  • A1 文件沙箱 containment：file_read/file_list 增加 isWithinRoot(resolved, projectRoot) 前缀断言，拒绝绝对路径越界；readFileContent 注入路径也须先过 containment + MAX_FILE_SIZE。复刻 Python file_tools.py:_resolve_path 的多根候选+白名单思路。
  • A2 SSRF 护栏：web_fetch 复用 async_is_safe_url 逻辑（解析 IP、拒绝 127/169.254/内网/元数据）；注入 httpClient 也必须先过 SSRF 检查+AbortSignal 超时；redirect:'manual' 禁止跳内网。
  • A3 审批强制：在 ToolRegistry.execute 中，若 permResult.needsConfirmation 或 definition.requiresConfirmation，调用 ApprovalManager.requestApproval 并等待结果；将 setPreChecksEnabled 改为不可运行时关闭（或仅限测试）。
  • A4 禁令牌硬化：shell_exec 由子串匹配改为“分词归一化 + 危险 token 黑名单 + 危险标志位(--force/-rf/-s/-q 组合) + AST/参数级拦截”，覆盖顺序/空格变体。

B. 错误恢复机制（P1）

  • B1 瞬态重试：在 ToolRegistry.execute 外包一层 retry 装饰器，仅对网络/LLM 类工具（429/5xx/ETIMEDOUT）做指数退避（最多 3 次，含 jitter），其余不重试。
  • B2 自愈接入 TS 路径：将 Python tool_self_healing.heal() 的能力（参数修正→替代工具→降级）以桥方式挂到 TS execute 的 catch 分支；补齐 RETRY 枚举的真实退避重试。
  • B3 熔断器：对付费/外部 API（image_generate/tts_speak/web_search）按错误率熔断，避免级联失败与费用失控。
  • B4 真超时中止：所有外部 IO 强制 AbortSignal.timeout；shell/子进程改用异步 spawn+child.kill，使超时真正生效（替换 execSync）。

C. 资源使用效率（P1）

  • C1 统一结果缓存：复用已有 python/agent/tools/tool_result_cache.py 与 TS system/result_cache.ts，按 (tool, normalizedArgs, version) 缓存幂等工具（web_fetch/idempotent、file_read、search），降低重复外部调用与费用。
  • C2 并发与配额：per-agent 信号量（如 maxConcurrentTools=4）；image_generate/tts_speak 增加 per-session 日配额与去重（相同 prompt hash 命中缓存）。
  • C3 流式/截断：web_fetch/file_read 大响应走分块读取与硬上限（已部分有），memory recall 加分页游标避免全量拉取。
  • C4 异步化：shell_exec、内存/文件读写改异步非阻塞，避免事件循环卡死（同时修复 P0-3）。

D. 能力协同（P2，价值最高）

  • D1 记忆↔检索↔搜索：memory_recall 优先走向量检索，命中不足时自动降级 web_search 并回填记忆（RAG 闭环），统一由 knowledge_query 编排。
  • D2 认知↔循环：emotion_detect/self_reflect 的真实 LLM 结果回灌 ReAct 循环的情绪/反思总线，驱动策略调整（如高负向情绪降速、反思建议进 evolution）。
  • D3 代码工具共享：code_generate/review/fix 共用同一 LLM 客户端、同一“生成物语法校验”与“安全扫描”中间件；code_fix 复用 Python code_edit_ast 的 preview_only+AST 校验写盘路径（消除“只建议不落地”错位）。
  • D4 统一门禁/缓存/观测：所有工具经由同一 execute 包装（Schema+Perm+Approval+Retry+Cache+Timeout+TraceId），保证一致的可观测性与治理。

E. 测试补齐（P1，可信度底座）

  • 为每个工具补 executor 级单测：重点覆盖错误路径（网络 429/5xx、文件不存在、注入缺失、参数越界）与安全路径（SSRF、路径穿越、禁令牌绕过）。
  • code_generate/review/fix 与 calendar 为零单测，须优先补齐行为断言（而非仅“已注册”）。
  • 将 Python async_is_safe_url 测试与 TS SSRF 守卫对齐，避免实现分裂。

F. 架构一致性（P0，治本）

  • 明确“谁为主”：按 AGENTS.md §0.1，记忆/LLM/认知/搜索应 Python 主实现。当前 web_search、file_*/shell_exec、memory_store 的 TS 本地实现与 Python 并存 → 选其一为 canonical，另一为桥/壳，杜绝双端 DRY 违规与行为漂移。
  • 能思对齐：TS 的 emotion_detect/self_reflect 要么改为经 PythonAgentBridge 调用 Python LLM 实现（与 Python 能力一致），要么在 DEF 描述中明确“轻量规则模式”并降级处理，避免 Agent 误以为有真实反思能力。
  • 缺依赖即失败而非静默成功：memory_store / tts_speak / self_reflect 等“无依赖就假装成功”的模式必须改为显式失败或明确降级标注。
